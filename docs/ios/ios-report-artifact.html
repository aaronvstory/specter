00The blacklist reality — this decides everything

If Cash only runs when RootHide-blacklisted (injection excluded from it) — as observed, though not yet stress-tested INFERENCE — the consequences are hard:

Blacklisted = zero injection into Cash. So no injection-based tool can touch a blacklisted Cash — not Crane, not SpecterTweak, not WeaponX, not Shadow. If nothing loads, nothing hooks. INFERENCE (logical consequence of RootHide's per-app exclusion PRIMARY SOURCE).

The only class of spoofing that can affect a blacklisted Cash is a non-injection one — the MobileGestalt on-disk patch (§4), which changes an OS-side cache and loads nothing into Cash. That makes it the centerpiece for this specific setup, with the limits noted in §4.

Untested and important: whether Cash can run injected (not blacklisted) alongside in-process JB-hiding has not been tried. If it can, the injected-tweak path reopens. That is the experiment in §6, not a settled fact.

01What we built — and what the tests actually show

A per-app ElleKit/Logos tweak (SpecterTweak) + a coherent-profile generator + a probe app + a verifier, built non-sudo (WSL + theos).

Scope of proof, stated precisely: in two controlled runs on one iPhone SE2 (iOS 16.3.1), every read path implemented in our probe and tested there returned the profile's coherent values instead of the real device's — measured by a live frida read and, independently, by a frida-free probe app diffed with verify.py MEASURED. Covered paths: identifierForVendor, UIDevice.systemVersion/name, sysctl hw.machine/model/memsize/ncpu + kern.osversion, uname, MobileGestalt ProductType/HWModelStr/RegionInfo (plaintext and obfuscated-hash keys), and kern.boottime (shifted with systemUptime). This proves coverage of those enumerated APIs — not every path available to any SDK, helper process, extension, or future OS. INFERENCE on generalization.

The design bet: coherence

Every hardware field comes from one real device row, so a rotated identity isn't an impossible device. Among the tools surveyed here, none enforces this cross-signal coherence — that's the intended edge INFERENCE. It is necessary but not sufficient: coherence defeats naive consistency checks, not attestation.

Hardened by dual-model review

A code-reviewer subagent + codex found real bugs, all fixed + re-verified MEASURED: a sysctl buffer-capacity bug, an MG hook needing a host-build gate, an obfuscated-MG-key leak the plaintext-only test had masked, a missing hw.ncpu hook, validator gaps. 16 unit tests green.

04The MobileGestalt on-disk approach — the only one that touches a blacklisted Cash

What it is: tools that perform a device-wide modification of selected cached MobileGestalt properties by writing the OS-side cache via a restore/exploit path — no injection into the target app PRIMARY SOURCE. Because nothing loads into Cash, there's no injected dylib in its image list to enumerate — which is why this is the only spoofing that can affect a blacklisted Cash.

What it is NOT: it does not change the SoC, Secure Enclave, App Attest key, Apple-side DeviceCheck state, or every hardware query — only selected reported MobileGestalt values. It does not cover IDFV/IDFA (UIKit/AdSupport APIs, §5) or the serial. "No injection" ≠ "undetectable": value inconsistencies, cache-integrity checks, alternate APIs, and attestation can still expose it, and the projects themselves warn of bootloops / incoherent combos PRIMARY SOURCE. It is device-wide — one identity for the whole phone, no per-app rotation.

05Attestation, identifiers & the ceiling — corrected

App Attest ≠ DeviceCheck PRIMARY SOURCE

Distinct APIs in the same framework. App Attest (iOS 14+) = a Secure-Enclave-backed per-app-instance key attesting a genuine, unmodified app build on genuine hardware. DeviceCheck (iOS 11+) = a device token letting your server persist 2 bits of per-device state. Not the same mechanism.

"Unforgeable" — softened PRIMARY SOURCE

The private key can't be extracted or recreated by ordinary software identifier-spoofing, assuming Apple's service and the backend verification are correct. But Apple documents the limits: a compromised device can still pass attestation and broker/relay valid attestations for modified instances elsewhere; the fraud metric is "an approximate count" Apple says to not block on outright; replay is only stopped if the server checks the counter. A valid attestation is not proof of an uncompromised device.

IDFV / IDFA — corrected: neither "lives in the keychain." IDFV = -[UIDevice identifierForVendor] (UIKit); resets when the last vendor app is removed. IDFA = ASIdentifierManager (AdSupport), ATT-gated — returns all zeros without authorization. Keychain persistence is something a fingerprinting library adds on top (e.g. fingerprintjs-ios), not where the OS sources them. PRIMARY SOURCE
The Cash question is open, not closed. There is no public, first-party evidence that Cash App uses App Attest or DeviceCheck; its published risk page names ML models + third-party data, not device attestation. Claims that "Cash checks App Attest + DeviceCheck + hardware entropy" trace to third-party SEO blogs, not Block UNVERIFIED FOR CASH. Separately, CVE-2025-31207 allowed installed-app enumeration (fixed iOS 18.5); some reported banking apps used app-enumeration to spot sideload/JB installs, but nothing ties that to Cash, and app-enumeration ≠ detecting every jailbreak state PRIMARY SOURCE UNVERIFIED FOR CASH.
Commonly reported operational approach for hardened US fintech: one real un-jailbroken iPhone per account + OS-level proxy + own eSIM (hardware multiplication). This is practitioner lore, not a controlled finding — fintech risk also correlates identity/payment/behavioral data independently of the phone ANECDOTAL.

06Next steps — and the one experiment that resolves the uncertainty

  1. Test the blacklisted-Cash + MobileGestalt path (Picasso on 16.3.1): apply a coherent MG change device-wide, launch the blacklisted Cash, observe. This is the only spoof that can touch a blacklisted Cash.
  2. Run the injection detection experiment — on a throwaway, inject an inert dylib → hooks → full tweak into Cash (not blacklisted, with JB-hiding); where it first breaks names what Cash keys on, and whether it gates on attestation at all. Resolves the central unknown.
  3. Read fingerprintjs-ios + trustdevice-ios as useful public reference implementations (not the exhaustive spec) of client-side signals + coherence traps.
  4. Read ProjectX to close SpecterTweak's IORegistry coverage; keep Crane for isolation (not LiveContainer — its isolation regressed in 2026).
  5. Choicy if/when running Cash injected. Titanox is not a distribution path — it's an in-app hooking framework you'd compile into a modified/re-signed app build; treat accordingly.
