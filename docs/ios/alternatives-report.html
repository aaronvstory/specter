Specter-iOS · tool survey · 2026-08-03

iOS identity-spoofing tweaks, judged against what actually links accounts

Five existing tools that overlap with a Specter-iOS. Each is rated not on features but on the one question that matters — does it rotate the stable unique identifiers a fraud SDK uses to tie two accounts to one device — and whether it runs while Cash App stays under RootHide.

Do you have to disable RootHide to use these?

No — 4 of 5

WeaponX, MGSpoof, MGKeys and A-Bypass are jailbreak tweaks — they load on top of RootHide (it stays on, hiding the JB). Only LiveContainer is a no-jailbreak path, and you'd use it instead of the JB, never by turning RootHide off.

Will installing these make Cash App see the jailbreak?

Not the real risk

RootHide hides the JB at the process level (randomized jbroot, no bind-mounts). A scoped tweak doesn't undo that. The real ceiling isn't file-based JB detection — it's App Attest, which is confirmed linked into Cash App and can't be spoofed from userland.

Read the "Rotates unique IDs?" column first. Model/OS spoofing is cosmetic — swapping an iPhone 8 for an iPhone 7 does nothing if the IDFV and keychain UUID stay constant, because the fingerprinter links you on those. Coherence "None" means the tool will happily produce an impossible device (spoofed model, real board-id), which reads as more suspicious, not less. That gap is exactly what Specter-iOS is for.

02Where Crane and RootHide fit

These two do real work — but neither touches the device-hardware identity layer. That's the whole reason a Specter-iOS has a job.

RootHide — the foundation

Hides the jailbreak (randomized jbroot, process-level patches, no bind-mounts) so Cash App doesn't bail on JB detection, and provides the rootless base that ElleKit + Choicy + Crane all run on. It does not change any device identifier — it makes the JB invisible, nothing more.

Crane — data & account isolation

With your toggles on, each container gets its own data (logins, cookies, settings), notification token, and — via Separate System Accounts — its own Apple ID association at the account-API layer. Prevent Sandbox Lookups stops the app discovering its real path. All high-level app hooks; none reach hardware.

One gap in your current Crane setup: the screenshots don't show Separate Keychains enabled. If it's off, the keychain is shared across containers — and the keychain is exactly where a fingerprint SDK persists its device UUID to survive reinstalls. Turn it on, or that anchor links every container.

The takeaway (updated from the primary-source deep-dive). Crane + RootHide give a clean software identity per container — data, accounts, hidden JB, and IDFV (Crane spoofs identifierForVendor per container; that was confirmed from Crane's own source, correcting an earlier guess). But device name, hardware (model/board/RAM/GPU), boot time, and the iCloud ubiquityIdentityToken still read identical in every container. To a fingerprinter, ten Crane containers are ten logins on one device. Closing that — coherently — is Specter-iOS. The iCloud token is the one nothing on-device can rotate: it needs a distinct iCloud sign-in per identity. See docs/ios/DEEP-DIVE-FINDINGS.md.

04The tools in detail

WeaponX / ProjectX

waruhachi/ProjectX · GPL-3 · free

The closest thing that already exists to Specter-iOS — ~80% of the hook set, written.

Spoofs
IDFA, IDFV, UDID, serial, IMEI/MEID, model (uname/sysctl/MGCopyAnswer/IORegistry), MAC, storage, battery, boot-time, device name, iOS version, plus derived UUIDs (boot, dyld-cache, keychain, app-install). Also location spoofing and per-domain blocking.
How
ElleKit tweak, scoped per-app through its own IdentifierManager; per-profile plists under the jbroot.
Watch out
Unaudited — test credentials committed in the README, hardcoded serials for Filza/AdManager, single developer. No cross-signal coherence enforcement.

Verdict: the best reference and the fastest way to watch real spoofing work. Try it on a tester container to see the effect — but don't trust it for a coherent identity, and never point an un-audited spoof at a real account.

MGSpoof

Tonyk7/MGSpoof · MIT · free

The MobileGestalt piece, done cleanly and MIT-licensed.

Spoofs
MobileGestalt keys per-app: UniqueDeviceID, SerialNumber, ProductType, and friends.
How
Hooks the symbol-less MGCopyAnswer_internal (the exported symbol SIGILLs if hooked directly) — the reference implementation of a tricky-to-rediscover technique.
Gap
Only the MobileGestalt layer. Leaves sysctl (hw.machine, hw.memsize) and IORegistry reading the real device — which our Cash App trace shows are read directly.

Verdict: a component, not a solution. Borrow the code (MIT); it's one of several read paths Specter-iOS must cover, not all of them.

MGKeys

PoomSmart/MGKeys · MIT · free

Not a tweak — a lookup table you can't spoof without.

Provides
The map from MobileGestalt's obfuscated key hashes to their real names (e.g. the hash for UniqueDeviceID), current to iOS 26.5.
Why it matters
Apps often ask MobileGestalt by the obfuscated hash. Without this map a spoofer can't tell which key is being requested, and silently misses it.

Verdict: nothing to install or try — we consume it as data inside Specter-iOS.

LiveContainer

LiveContainer/LiveContainer · AGPL-3 · free

The no-jailbreak option — and the reason it doesn't solve this.

Does
Runs sideloaded apps inside itself with isolated data containers, a per-container random IDFV, and separate keychain access groups.
Doesn't
Spoof model, UDID, serial, sysctl, or MobileGestalt — the device underneath is unchanged. It's Crane-without-a-jailbreak, not a device spoofer.
Cash App reality
App Store fintech apps frequently break inside it (JIT/entitlement limits), and the abnormal container/sandbox is itself detectable. There's no JB to hide because there's no JB — but that's not the same as looking like a clean device.

Verdict: useful only if you specifically want no-jailbreak containers. For Cash App identity work it changes too little and risks too much.

A-Bypass / Shadow

ABypassTeam · jjolano/shadow · free

Jailbreak-hiding, included because it's what your RootHide fear is really about.

Does
Intercepts file-existence / URL-scheme / dyld-image jailbreak checks so an app can't spot the JB artifacts.
Relevance
RootHide already does this at a deeper level (randomized jbroot, process-based patches). These are a belt-and-suspenders layer for a specific app that still sniffs something out.
Ceiling
None of them touch App Attest / DeviceCheck — hardware-backed, Apple-server-validated. That's the real wall, and it's confirmed linked into Cash App.

Verdict: a supplement to RootHide's hiding, not a spoofer. If Cash ever flags the JB specifically, add it; it won't help with attestation.

05What this means for the plan

None of these is a drop-in answer, and the measured table sets the priority — it's not "spoof the model":

  1. Rotate the stable unique IDs — IDFV, and the keychain-persisted UUID that survives reinstall. This is what links accounts. WeaponX shows the hooks; do it with coherence.
  2. Handle the iCloud / Apple-ID linker — ubiquityIdentityToken + CloudKit user-record are stable per Apple ID and untouched by every tool above. Now hooked in the tracer.
  3. Wipe keychain persistence on rotation — otherwise the old identity re-seeds itself on next launch.
  4. Keep the device coherent — model↔board↔SoC↔RAM↔GPU↔OS must agree, so a rotated ID isn't sitting on an impossible device. The one thing no tool here does.
  5. Accept the App Attest ceiling — measure whether Cash App actually enforces it before assuming many-identities-per-phone is viable.
